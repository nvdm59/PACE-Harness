# Trainer naming check: "CGRPO" (NumPy) vs the GRPO/DAPO LLM backends

1. **NumPy `train_cgrpo` (sim replay) uses a group-relative advantage with the group mean as the baseline, and no std normalisation.** `pace/train_offline.py:240,243`: `b = sum(rs) / group` … `ADV.append(r - b)`. The lookup form does the same at `:159`: `adv = (r - r.mean(1, keepdims=True)).ravel()`.
2. **It takes one plain score-function step per batch, with no importance ratio, no ratio clipping, and no KL/reference term.** `:245-246`: `g = pol.grad_logits_batch(X, M, A, ADV * pol.eps_score_weights(X, M, A, serve_eps))`; `pol.W += lr * g / (batch * group)` (lookup: `:161-162`). `grad_logits_batch` (`pace/controller.py`) returns `sum_i coef_i * d log softmax(a_i|x_i)/dW`. `train_offline.py` contains no ratio, clip-of-ratio or KL code. Its only `np.clip` is the AWR weight at `:114`, which belongs to a different trainer.
3. **It is on-policy.** Every batch is freshly sampled from the current iterate as served. `:229`: `a, _ = pol.act(x, legal, rng, use_mix=False)  # sampled as served (eps included)`; lookup `:154`: `P = pol.probs_batch(X, Mb, eps=serve_eps, use_mix=False)`. There is one gradient step per sample, so a PPO ratio would be identically 1, and clipping it would be a no-op. Precise name: **on-policy group-baseline (REINFORCE-style) policy gradient on a Lagrangian reward, with PI-damped dual ascent and iterate averaging**. GRPO's group-mean baseline is the only GRPO ingredient. The eps-score weight (`eps_score_weights`) is an exact score correction for the ε-mixed served policy; it is not an importance ratio.
4. **The LLM backends use clipped GRPO/DAPO objectives with a KL term.**
   - TRL, `pace/llm/backends/trl_grpo.py:201-202`: `GRPOConfig(..., beta=beta, ..., epsilon=0.2, epsilon_high=clip_high, ...)` (DAPO clip-higher 0.2/0.28, KL β; the run metadata records `"loss_type": "dapo"`). The phase-1 trainer `pace/llm/train_grpo_modal.py:160-165` uses TRL `GRPOConfig` with `beta=beta` and TRL's default clip ε = 0.2.
   - verl, `pace/llm/backends/verl_config.yaml:26` `algorithm.adv_estimator: grpo`; `:46-51` `use_kl_loss: true`, `kl_loss_coef: 0.02`, `clip_ratio_low: 0.2`, `clip_ratio_high: 0.2`, `loss_agg_mode: token-mean`; DAPO recipe `:96-100` `kl_loss_coef: 0.05`, `clip_ratio_low: 0.2`, `clip_ratio_high: 0.28`.
   - NeMo-RL, `pace/llm/backends/nemo_rl_config.yaml:32-35` `reference_policy_kl_penalty: 0.02`, `ratio_clip_min: 0.2`, `ratio_clip_max: 0.2`; DAPO overrides `:125-127` `ratio_clip_min=0.2`, `ratio_clip_max=0.28`, `reference_policy_kl_penalty=0.05`, plus dynamic sampling (`:123-124`).
5. **Consequence for naming.** "Constrained GRPO" overstates what the NumPy trainer shares with GRPO. Only the LLM backends are GRPO/DAPO in the clipped-surrogate sense.
